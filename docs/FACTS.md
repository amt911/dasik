# FACTS — verified facts an agent would otherwise re-derive

> **Convention** (see `AGENTS.md` § *Agent orchestration*): when you verify something against this
> repo or the running system that the next agent would otherwise have to look up again, append a
> one-line fact here — with **how** you verified it. Facts only, never plans or opinions.
>
> This is **not** the gotchas log. That one holds what is *not* deducible from the code and outlives
> the branch; this holds what is perfectly deducible and merely expensive to re-derive, and it may go
> stale and die with the branch.
>
> Format: `- `<name>` — <the fact, in one line>. *(verified: <how>, <YYYY-MM-DD>)*`

- `FACT-PR-1` — `gpg --homedir /etc/pacman.d/gnupg --with-colons --list-keys <FINGERPRINT>` is the keyring-listing command, and it was measured to behave identically **both natively (`--target /`) and run literally through `arch-chroot`**, not just reasoned about: measurement 10 bind-mounted `/` onto `/mnt` and ran the full add/lsign/list/delete cycle via `arch-chroot /mnt <cmd>` — absent-key listing gave the same rc=2 with the same `gpg: WARNING: unsafe permissions on homedir '/etc/pacman.d/gnupg'` / `gpg: error reading key: No public key` / stray `tru:` line as the native case; `pacman-key --add`/`--lsign-key`/`--delete` all returned rc=0 through the chroot; and the lsigned-key listing taken through `arch-chroot` in the same boot, diffed byte-for-byte against the native listing of the same keyring (same real `/etc/pacman.d/gnupg`, reached via the bind mount), came back `PROBE-10D-DIFF=IDENTICAL` — no extra gpg-agent/keyboxd warning appeared under chroot. `pacman-key --list-keys <FINGERPRINT>` (no `--with-colons`) was separately measured for comparison, natively only (not through `arch-chroot`), on the absent-key case, and returns rc=1 with `==> ERROR: A specified key could not be listed.` and no parseable colon data, versus the raw `gpg` call's rc=2 with a stray `tru:` line (emitted regardless of which key was requested, interfering with colon-field parsing). *(verified: guest probe — `gpg --with-colons --list-keys` and `pacman-key --add`/`--lsign-key`/`--delete` measured both natively and through arch-chroot; `pacman-key --list-keys` (no `--with-colons`) natively only — 2026-09-16)*
- `FACT-PR-2` — "Trusted" (i.e. locally signed via `pacman-key --lsign-key`) shows in `gpg --with-colons` two ways: the validity field (2nd column of `pub:`/`uid:`/`sub:`) flips from `-` to `f`, AND `--list-sigs` gains a `sig:` line from `Pacman Keyring Master Key <pacman@localhost>` whose sig-class field (11th column) carries a trailing `l` (`10l`) marking it LOCAL/non-exportable, versus the key's own self-signatures which are `13x`/`18x`. The sig-class suffix is the reliable signal — the validity column alone reaches `f` via ordinary web-of-trust too, not just a local pacman-key signature. *(verified: guest probe, 2026-09-16)*
- `FACT-PR-3` — `arch-chroot` mounts a PRIVATE `/tmp`: a file created in the host's `/tmp` before chrooting (`probe-host`) is invisible inside `arch-chroot /mnt` (`ls: cannot access '/tmp/probe-host': No such file or directory`) because `findmnt -n /tmp` inside the chroot shows a fresh `tmp tmpfs rw,nosuid,nodev,inode64,huge=advise` mount; `/var/tmp` IS shared (a file placed there before chrooting, `amt911.gpg`, is visible inside) — so any temp file `PacmanRepositoriesAction.apply` writes for cross-context reuse (the downloaded key, the single-repo `pacman.conf`) must go under `/var/tmp`, never `/tmp`. *(verified: guest probe, 2026-09-16)*
- `FACT-PR-4` — `pacman -Sy --config <conf with only [options]+[amt911]>` leaves `core.db`/`extra.db` mtimes byte-identical before and after (`core.db` 1789472587, `extra.db` 1789591513, unchanged) and deletes neither file from `/var/lib/pacman/sync/` — it only adds `amt911.db`/`amt911.db.sig`. Mtimes alone do NOT discriminate a scoped `-Sy` from a full one when the databases are already current: a full `pacman -Sy` also leaves an up-to-date `core.db`/`extra.db`'s mtime unchanged, since it skips the download once the local copy already matches the remote. The discriminating evidence is the apply stream, not the mtimes: the guest's `-v` apply (`PACREPO-G`, `dasik apply … -v`) names only `amt911` downloading (`PACREPO-SYNC-TOUCHED-AMT911`) and never mentions core/extra (`PACREPO-SYNC-ISOLATED-CORE`/`PACREPO-SYNC-ISOLATED-EXTRA`, both rc=0 in `/var/tmp/dasik-vmtest-pacrepo-v2/drive-final-green.log`); reverting the single-repo `pacman.conf` to a plain `-Sy` (no `--config`) turns those same two checks red — `PACREPO-SYNC-ISOLATED-CORE-RC=1`/`PACREPO-SYNC-ISOLATED-EXTRA-RC=1` in `/var/tmp/dasik-vmtest-pacrepo-redproof2/drive.log` and `drive-red2.log` (mtime-unchanged checks stayed rc=0 in the same red run — confirming mtimes cannot tell the two apart). *(verified: guest probe, 2026-09-16)*
- `FACT-PR-5` — `/usr/share/pacman/keyrings/*-trusted` lines are `<40-hex-uppercase-fingerprint>:4:` (fingerprint, literal trust-level `4`, trailing empty field), one per trusted key — e.g. `archlinux-trusted`'s first three lines are `2AC0A42EFB0B5CBC7A0402ED4DC95B6D7BE9892E:4:`, `3572FA2A1B067F22C58AF155F8B821B42A6FDCD7:4:`, `69E6471E3AE065297529832E6BA0F5A2037F4F41:4:`. - `FACT-RFD-1` — the kernel resolves a bare btrfs `compress`/`compress-force` mount option to an explicit compression LEVEL: a config declaring `mount_options: ["compress-force=zstd", "noatime"]` on the root `@` subvolume produces a boot entry written verbatim as `rootflags=compress-force=zstd,noatime,subvol=@` (no level), but `findmnt -o OPTIONS` on the same live mount reports `noatime,compress-force=zstd:3,...` — the default level (`3`) filled in. This is why a captured config's derived `rootflags=` can never string-match the boot entry it was captured from without an equivalence check (`KernelCmdlineAction._rootflags_equivalent`). *(verified: `scripts/vmtest/qemu.sh install-driven`+`drive` against `config/vm-rootflags-drift.json`/`guest-rootflags-drift.sh` — RFD-CAPTURED-ROOT-OPTS: `['noatime', 'compress-force=zstd:3']` in `/var/tmp/dasik-vmtest-rootflags/drive-green2.log`, 2026-09-17)*. The "`zlib`'s default is also `3`; `lzo` has no level at all" half of this fact was NOT measured at the time and is superseded by the full table in `FACT-RFD-3` below (round 1 review, N3) — it IS confirmed there.
- `FACT-RFD-2` — a real ArchISO guest confirms `KernelCmdlineAction.apply`'s replace-in-place fix actually replaces rather than duplicates: applying a `rootflags=` change against an entry that already carries one leaves EXACTLY one `rootflags=` token on the sd-boot entry afterward (`options … rw rootflags=noatime,compress-force=zstd:1,subvol=@`, one token, in `drive-green2.log`), and `rollback` restores the entry to exactly one token with the prior value (`rootflags=compress-force=zstd,noatime,subvol=@`). *(verified: same guest run as FACT-RFD-1, 2026-09-17)*
- `FACT-RFD-3` — the full btrfs compression-LEVEL clamping/normalization table, measured on a loopback `mkfs.btrfs` image mounted with the guest's own running kernel (`findmnt -no OPTIONS` after each mount, `scripts/vmtest/guest-rootflags-drift.sh`'s `RFD-MEASURE-*` section): `compress=zstd`→`zstd:3`, `compress-force=zstd`→`zstd:3`, `compress-force=zstd:0`→`zstd:3`, `compress-force=zstd:1`→`zstd:1` (unclamped), `compress-force=zstd:15`→`zstd:15` (unclamped), `compress-force=zstd:16`→`zstd:15` (**clamped down** — confirms the reviewer's hypothesis), `compress=zlib`→`zlib:3`, `compress=zlib:0`→`zlib:3`, `compress=zlib:9`→`zlib:9` (unclamped), `compress=zlib:12`→`zlib:9` (**clamped down**), `compress=lzo`→`lzo` (no level, confirmed — matches `FACT-RFD-1`'s original claim), bare `compress` (no algorithm at all) →`zlib:3`, bare `compress-force` →`zlib:3` (**zlib is the kernel's default algorithm when none is named at all — NOT zstd**, also confirming the reviewer's hypothesis), `compress=no` → no `compress*` option reported at all (compression fully off, not even a literal token).
  Correction (re-review round 2, SF-3): what `plan` actually diffs against is the BOOT ENTRY `apply` last wrote, never `findmnt`/the machine directly — so an explicit `zstd:16`/`zlib:12` in a config that itself wrote that entry stays silent regardless of the clamp; the clamp only ever surfaces through a `sync → check → plan` round trip (a captured `zstd:15` against an entry still spelled `zstd:16`), which used to cost exactly **one** spurious INSTALL and then converge — never "forever" as this fact previously (wrongly) claimed. SF-2 (round 2) now normalizes exactly these four clamped spellings plus the two bare names for EQUIVALENCE (`partition_utils.normalize_compress_value`/`normalize_compress_option`), so even that one-INSTALL round trip is gone: a declared `zstd:16` and a captured `zstd:15` are recognized as the same setting and `sync → plan` is silent without an apply. Unmeasured levels (`zstd:17`+, `zlib:10`/`11`/`13`+, a negative zstd level, `lzo:N`) are deliberately left un-normalized — the table above is exactly what was measured, nothing extrapolated. *(verified: `scripts/vmtest/qemu.sh drive` against `config/vm-rootflags-drift.json`/`guest-rootflags-drift.sh`, `/var/tmp/dasik-vmtest-rootflags-r1/drive-green2.log`, 2026-09-17; the correction and SF-2's normalization re-verified in the round-2 guest run, see `FACT-RFD-6` below)*
- `FACT-RFD-4` — S2 (round 1 review): `strictatime` is NEVER reported by findmnt on btrfs — it is the ABSENCE of `relatime`/`noatime`, not a string the kernel emits. Measured on the same loopback image: `mount -o strictatime` → `findmnt` reports `rw,ssd,discard=async,space_cache=v2,subvolid=5,subvol=/` (no atime word at all); `noatime` → `...,noatime,...`; `nodiratime` → `...,nodiratime,relatime,...` (relatime stays, since nodiratime only suppresses directory atime updates); `lazytime` → `...,relatime,lazytime,...`; `relatime` → `...,relatime,...`. This independently reproduces the reviewer's `unshare -Urm`+tmpfs measurement on the real btrfs code path, and is why `strictatime` was removed from `DiskPartitionAction._DECLARABLE_BTRFS_FLAGS` — a whitelist entry for a string the kernel can never report was dead code that also made a unit test pack an unreachable findmnt row. *(verified: same guest run as `FACT-RFD-3`, `RFD-MEASURE-STRICTATIME`/`RFD-MEASURE-NOATIME`/`RFD-MEASURE-NODIRATIME`/`RFD-MEASURE-LAZYTIME`/`RFD-MEASURE-RELATIME` in `drive-green2.log`, 2026-09-17)*
