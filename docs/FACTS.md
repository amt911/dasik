# FACTS — verified facts an agent would otherwise re-derive

> **Convention** (see `AGENTS.md` § *Agent orchestration*): when you verify something against this
> repo or the running system that the next agent would otherwise have to look up again, append a
> one-line fact here — with **how** you verified it. Facts only, never plans or opinions.
>
> This is **not** the gotchas log. That one holds what is *not* deducible from the code and outlives
> the branch; this holds what is perfectly deducible and merely expensive to re-derive, and it may go
> stale and die with the branch.
>
> Format: `- `<name>` — <the fact, in one line>. *(verified: <how>, <YYYY-MM-DD>)*`

- `FACT-PR-1` — `gpg --homedir /etc/pacman.d/gnupg --with-colons --list-keys <FINGERPRINT>` is the keyring-listing command, and it was measured to behave identically **both natively (`--target /`) and run literally through `arch-chroot`**, not just reasoned about: measurement 10 bind-mounted `/` onto `/mnt` and ran the full add/lsign/list/delete cycle via `arch-chroot /mnt <cmd>` — absent-key listing gave the same rc=2 with the same `gpg: WARNING: unsafe permissions on homedir '/etc/pacman.d/gnupg'` / `gpg: error reading key: No public key` / stray `tru:` line as the native case; `pacman-key --add`/`--lsign-key`/`--delete` all returned rc=0 through the chroot; and the lsigned-key listing taken through `arch-chroot` in the same boot, diffed byte-for-byte against the native listing of the same keyring (same real `/etc/pacman.d/gnupg`, reached via the bind mount), came back `PROBE-10D-DIFF=IDENTICAL` — no extra gpg-agent/keyboxd warning appeared under chroot. `pacman-key --list-keys <FINGERPRINT>` (no `--with-colons`) was separately measured for comparison, natively only (not through `arch-chroot`), on the absent-key case, and returns rc=1 with `==> ERROR: A specified key could not be listed.` and no parseable colon data, versus the raw `gpg` call's rc=2 with a stray `tru:` line (emitted regardless of which key was requested, interfering with colon-field parsing). *(verified: guest probe — `gpg --with-colons --list-keys` and `pacman-key --add`/`--lsign-key`/`--delete` measured both natively and through arch-chroot; `pacman-key --list-keys` (no `--with-colons`) natively only — 2026-09-16)*
- `FACT-PR-2` — "Trusted" (i.e. locally signed via `pacman-key --lsign-key`) shows in `gpg --with-colons` two ways: the validity field (2nd column of `pub:`/`uid:`/`sub:`) flips from `-` to `f`, AND `--list-sigs` gains a `sig:` line from `Pacman Keyring Master Key <pacman@localhost>` whose sig-class field (11th column) carries a trailing `l` (`10l`) marking it LOCAL/non-exportable, versus the key's own self-signatures which are `13x`/`18x`. The sig-class suffix is the reliable signal — the validity column alone reaches `f` via ordinary web-of-trust too, not just a local pacman-key signature. *(verified: guest probe, 2026-09-16)*
- `FACT-PR-3` — `arch-chroot` mounts a PRIVATE `/tmp`: a file created in the host's `/tmp` before chrooting (`probe-host`) is invisible inside `arch-chroot /mnt` (`ls: cannot access '/tmp/probe-host': No such file or directory`) because `findmnt -n /tmp` inside the chroot shows a fresh `tmp tmpfs rw,nosuid,nodev,inode64,huge=advise` mount; `/var/tmp` IS shared (a file placed there before chrooting, `amt911.gpg`, is visible inside) — so any temp file `PacmanRepositoriesAction.apply` writes for cross-context reuse (the downloaded key, the single-repo `pacman.conf`) must go under `/var/tmp`, never `/tmp`. *(verified: guest probe, 2026-09-16)*
- `FACT-PR-4` — `pacman -Sy --config <conf with only [options]+[amt911]>` leaves `core.db`/`extra.db` mtimes byte-identical before and after (`core.db` 1789472587, `extra.db` 1789591513, unchanged) and deletes neither file from `/var/lib/pacman/sync/` — it only adds `amt911.db`/`amt911.db.sig`. Mtimes alone do NOT discriminate a scoped `-Sy` from a full one when the databases are already current: a full `pacman -Sy` also leaves an up-to-date `core.db`/`extra.db`'s mtime unchanged, since it skips the download once the local copy already matches the remote. The discriminating evidence is the apply stream, not the mtimes: the guest's `-v` apply (`PACREPO-G`, `dasik apply … -v`) names only `amt911` downloading (`PACREPO-SYNC-TOUCHED-AMT911`) and never mentions core/extra (`PACREPO-SYNC-ISOLATED-CORE`/`PACREPO-SYNC-ISOLATED-EXTRA`, both rc=0 in `/var/tmp/dasik-vmtest-pacrepo-v2/drive-final-green.log`); reverting the single-repo `pacman.conf` to a plain `-Sy` (no `--config`) turns those same two checks red — `PACREPO-SYNC-ISOLATED-CORE-RC=1`/`PACREPO-SYNC-ISOLATED-EXTRA-RC=1` in `/var/tmp/dasik-vmtest-pacrepo-redproof2/drive.log` and `drive-red2.log` (mtime-unchanged checks stayed rc=0 in the same red run — confirming mtimes cannot tell the two apart). *(verified: guest probe, 2026-09-16)*
- `FACT-PR-5` — `/usr/share/pacman/keyrings/*-trusted` lines are `<40-hex-uppercase-fingerprint>:4:` (fingerprint, literal trust-level `4`, trailing empty field), one per trusted key — e.g. `archlinux-trusted`'s first three lines are `2AC0A42EFB0B5CBC7A0402ED4DC95B6D7BE9892E:4:`, `3572FA2A1B067F22C58AF155F8B821B42A6FDCD7:4:`, `69E6471E3AE065297529832E6BA0F5A2037F4F41:4:`. Only `archlinux-trusted` exists on this minimal image (no other `*-keyring` package installed), so `PacmanRepositoriesAction.actual()`'s exclusion glob (`*-trusted`) was exercised against just the one file. *(verified: guest probe, 2026-09-16)*
- `FACT-SFRM-1` — `config/vm-btrfs-snapper.json` does **not** actually give `.snapshots` a separate mount: its `btrfs_subvolumes` list is only `@`/`@home`. Dasik's OWN recommended layout — the one `SnapperAction._create_config`'s wiki-dance is written for — is `dasik/lib/wizard/recipes.py`'s `_SUBVOLUMES`: `@`, `@home`, `@log`, `@pkg`, `@.snapshots` (mounted at `/.snapshots`). A probe config without the extra subvolume never exercises the dance at all: `_is_snapshots_mount` sees no separate mount, `snapper create-config` gets to make its own nested `.snapshots` directly. *(verified: read config/vm-btrfs-snapper.json + dasik/lib/wizard/recipes.py, cross-checked against `btrfs subvolume list /` output from a guest install of each, 2026-09-17)*
- `FACT-SFRM-2` — `snapper --no-dbus -c <name> delete-config` on `.snapshots` as snapper's OWN nested subvolume (no separate mount): deletes every numbered snapshot subvolume (`.snapshots/<N>/snapshot`) **and** the `.snapshots` container subvolume itself (it vanishes from `btrfs subvolume list /` and `/.snapshots` no longer exists — `ls: cannot access '/.snapshots': No such file or directory`), clears the name from `/etc/conf.d/snapper`'s `SNAPPER_CONFIGS` (`SNAPPER_CONFIGS=""`), removes `/etc/snapper/configs/<name>`, and returns **rc=0** — a clean, complete removal. A harmless internal `umount failed errno:22 (Invalid argument)` is printed (snapper tries to unmount `.snapshots` defensively even though it was never a real mount) but does not affect the outcome. *(verified: guest probe, config/vm-snapper-probe.json without `@.snapshots`, scripts/vmtest/guest-snapper-probe.sh, 2026-09-17)*
- `FACT-SFRM-3` — the SAME `snapper --no-dbus -c <name> delete-config`, on dasik's REAL recommended layout — `.snapshots` a SEPARATELY mounted `@.snapshots` subvolume — **fails**: it deletes the individual snapshot subvolumes fine, then `Btrfs.cc(deleteConfig):195 delete subvolume failed, btrfs_util_delete_subvolume_fd() failed, errno:22 (Invalid argument)` / `Deleting config failed (deleting snapshot failed).`, **rc=1**. Worse, it is not a clean no-op failure: `mountpoint -q /.snapshots` reported **rc=0 before** the attempt (genuinely mounted — `PROBE-MOUNTPOINT-BEFORE-RC: 0` in `scratchpad/probe2-clean.txt:19-20`, confirmed by `findmnt -no SOURCE,OPTIONS` showing a real `subvol=/@.snapshots` line) and **rc=32 after** (`PROBE-MOUNTPOINT-AFTER-RC: 32`, `findmnt` now empty) — i.e. `mountpoint -q`'s rc **is** diagnostic here (0 = mounted, 32 = util-linux's "not a mountpoint"), and `_is_snapshots_mount`'s `== 0` check is exactly right; the earlier wording of this FACT cast doubt on that and was wrong. Its `/etc/fstab` entry is also GONE after the failed call (`mount /.snapshots` afterward: `can't find in /etc/fstab`, and `grep snapshots /etc/fstab` matches nothing where it matched before), while `/etc/snapper/configs/<name>` and `/etc/conf.d/snapper`'s `SNAPPER_CONFIGS` are UNCHANGED (config still fully registered). A machine left worse off than before the call, reported as a failure. This is why `SnapperAction._delete_config` never calls this command at all and does the removal itself (delete each numbered snapshot subvolume + drop the config's own metadata by hand), only additionally deleting the `.snapshots` container subvolume when it is NOT a separate mount. *(verified: guest probe, config/vm-snapper-probe.json WITH `@.snapshots`, same guest-snapper-probe.sh, 2026-09-17; re-read from the raw transcript `scratchpad/probe2-clean.txt` during the fix-round review, 2026-09-17)*
- `FACT-SFRM-4` — a PLAIN `snapper -c <name> list` (WITHOUT `--no-dbus`) can return STALE data for a config just deleted via `--no-dbus`: after `FACT-SFRM-2`'s clean `--no-dbus` delete-config (config file gone, `.snapshots` subvolume gone), a plain `snapper -c root list` still printed the pre-deletion 3-row table (current/probe1/probe2) — the D-Bus daemon (activated earlier in the same boot by an earlier non-`--no-dbus` `snapper -c root create` call) had cached the config and was never told about the out-of-band deletion. This is why `_delete_config` never depends on any snapper CLI call to report correctly, and why the guest scenario checks `--no-dbus`, not a bare `list`, for its post-removal assertion. The earlier wording of this FACT additionally claimed `snapper --no-dbus -c root list` itself still succeeds (rc=0, a fresh empty listing) once the config is genuinely gone — that claim was **wrong**: the `--no-dbus` rc=0 listing actually measured in the raw probes (`scratchpad/probe2-clean.txt`'s `PROBE-LIST-AFTER-NODBUS-RC=0`) was taken after `FACT-SFRM-3`'s **failed** delete-config, where the config file was still fully registered — not after a genuine deletion, so it is not evidence about what `--no-dbus -c <name> list` does once the config is truly gone. Once dasik's own `_delete_config` genuinely removes the config file (`os.remove` on `/etc/snapper/configs/<name>`), `snapper --no-dbus -c <name> list` has no such config to read and **fails** — directly MEASURED on the host (not inferred from a guest run that could not tell "missing config" apart from "missing binary"): `snapper --no-dbus -c definitely-not-a-config-xyz list` prints `Config 'definitely-not-a-config-xyz' not found.` and exits **rc=1** (snapper 0.13.1).
